# Островок AI — Техническое задание: Этап 1 / Data & Agent Foundation

**Версия:** 1.0 · **Дата:** 2026-10-26 · **Статус:** согласован приоритет, проектное ТЗ · **Регион-кандидат:** Центральный Сочи + Адлер.

## 1. Контекст и продуктовая цель

Островок AI — модуль интеллектуального обогащения карточек отелей. Пользователь формулирует запрос естественным языком. Сервис возвращает не просто похожие варианты, а объясняет, какие условия подтверждены, какие только рассчитаны, какие неизвестны и на какие вопросы ожидается ответ отельера.

Первый этап посвящён достоверности и технической вертикали данных. Ключевой демонстрационный путь:

**проверяемый источник → сырое свидетельство → нормализованное утверждение → георасчёт/верификация → разрешённое значение → поиск/API → объяснение**.

При этом действующий репозиторий `GrekEv/ostrovok` остаётся основой: Go API, PostgreSQL, Telegram Mini App, свайпы и пользовательские предпочтения. Отдельный ранее созданный SQLite/FastAPI-демомодуль — справочный прототип, но не альтернативная продуктовая база.

## 2. Рамки и приоритет

### Входит в этап 1

1. Аудит исходного Go API и структуры PostgreSQL; фиксация контрактов интеграции.
2. Пилотный каталог **20 реальных отелей** внутри выбранной области; у каждого координаты и канонический идентификатор, с проверкой дублей.
3. Реестр характеристик, версии определений и политики сбора/проверки.
4. Не менее **трёх реально работающих коннекторов** из разных типов: OSM/Overpass, Wikidata/Wikipedia, Wikimedia Commons; муниципальные реестры — только после отдельной проверки доступа и геопривязки. Вместо невозможного источника не выдавать фиктивный импорт.
5. Геоалгоритм для расстояния до пляжа и маршрута пешком при наличии пешеходного роутера; фиксация способа расчёта.
6. История доказательств, источники, авторство, даты, уверенность, сроки применимости, конфликты, ручное разрешение.
7. Отдельный сценарий вопросов отельеру: создание, ответ свободным текстом, извлечение нескольких полей, статус проверки.
8. Пайплайн повторного сбора с очередью задач, идемпотентностью, тайм-аутами и ограничениями запросов.
9. REST API и техническая консоль / OpenAPI для воспроизводимой демонстрации.
10. Размеченная проверочная выборка, метрики, тесты и быстрый seed-режим.

### Не входит в этап 1

Платежи, реальные бронирования, интеграции с OTA/PMS отельеров, полировка всех пользовательских экранов, полноценный Flutter-релиз, генеративные описания без привязки к источникам, универсальная поддержка всех регионов.

**Обязательная граница:** данные о ценах и доступности номеров не считаются актуальными, пока не подключён специализированный поставщик; на этом этапе они исключены из достоверных утверждений.

## 3. Роли и права

| Роль | Может | Не может |
|---|---|---|
| Гость / traveler | искать, изучать доказательства, сравнивать, сохранять | менять утверждения и статус проверки |
| Отельер / hotelier | отвечать за закреплённый отель, подтверждать/оспаривать информацию | изменять чужие отели или удалять журнал |
| Контент-аналитик / reviewer | видеть конфликты и источник, принимать решение с причиной | изменять системные права |
| Администратор / admin | настройки источников, каталог, задачи, роли, оценки | переписывать неизменяемый архив доказательств |
| Фоновый агент / service | выполнять разрешённые коннекторы и создавать кандидаты в факты | помечать неподтверждённое как verified без политики/проверки |

Токен Telegram валидируется сервером; привязка отельера к объекту хранится отдельно от Telegram user_id. Разработка вне Telegram допускается лишь через явно разрешённый dev login, отключённый в production.

## 4. Единица истины и типы доказательств

### 4.1 Сущности

- `hotel`: каноническая карточка объекта, координаты, название, адрес, состояние совпадения с исходным каталогом.
- `hotel_external_id`: соответствие `(provider, external_id) → hotel_id`, защита от слияния одноимённых объектов.
- `room_type`: тип номера, необязательный, нужен для фактов «вид из номера» и «звукоизоляция номеров».
- `feature_definition`: `key`, `version`, `type`, `unit`, `scope`, `collection_policy`, `resolution_policy`, `ttl`, описание на русском, валидация и необходимые источники.
- `source_record`: источник, исходный URL/ID, юридические условия/лицензия, `retrieved_at`, `published_at`, `valid_from`, `valid_to`, контрольная сумма ответа, текстовый фрагмент / ссылка на архив.
- `fact_assertion`: утверждение об объекте, признаки, тип значения, метод (`observed`, `derived`, `hotelier_reported`), confidence и поле контекста (номер, этаж, даты).
- `resolved_fact`: актуальное результирующее значение для конкретного объекта и контекста; содержит список `assertion_ids`, статус и причину.
- `fact_conflict`: конфликт несовместимых утверждений, статус, разрешение, кто и когда решил.
- `geo_feature`: береговые линии, пляжи, дороги, парки для животных, стройки и временные события с геометрией и периодом.
- `enrichment_job` / `job_attempt`: задачa, этапы, коннектор, статус, ошибки, повторные попытки, версия алгоритма.
- `hotelier_question`, `hotelier_answer`, `extraction_candidate`: переписка, сырой текст и структурированные кандидаты.
- `evaluation_item`: эталонное значение, источник разметки, качество проверки, решение рецензента.
- `audit_event`: журнал критичных изменений.

### 4.2 Неизменяемые поля любого доказательства

`assertion_id`, `hotel_id`, `feature_key`, `subject_type`, `subject_id`, `value`, `unit`, `source_record_id`, `method`, `confidence`, `confidence_basis`, `observed_at`, `retrieved_at`, `valid_from`, `valid_to`, `algorithm_version`, `created_at`.

Confidence — **оценка качества доказательства**, а не вероятность того, что LLM «прав». Источник никогда не подменяется строкой `AI` без ссылки на документ, ответ отельера или результат расчёта.

### 4.3 Состояния

- `verified` — подтверждён предусмотренной политикой комбинацией независимых свидетельств либо уполномоченным подтверждением соответствующей области.
- `estimated` — рассчитано/косвенно выведено; обязательно показывается метод, точность и допущения.
- `reported` — прямо заявлено отельером, но не прошло дополнительную проверку.
- `conflicted` — есть несовместимые актуальные свидетельства.
- `unknown` — отсутствуют пригодные сведения; отсутствие записи не означает `false`.
- `stale` — срок актуальности/валидности истёк.

Значение `verified` не присваивается автоматически на основании только высокого confidence; оно выводится по политике источника и проверяемого признака.

## 5. Реестр характеристик / пилот

Обязательные: `beach_walk_minutes`, `beach_route_m`, `coast_straight_m`, `pets_allowed`, `pet_max_weight_kg`, `pet_fee`, `room_window_azimuth_deg`, `sunset_view`, `noise_risk`, `active_construction_nearby`, `building_year`, `building_history`, `rooftop_terrace`, `dog_park_walk_minutes`.

Для каждого признака определить: тип, размерность, области действия (`hotel`/`room_type`/`hotel_date`/`room_date`), прямые и производные источники, сроки актуальности, порог отправки вопроса отельеру, допустимые значения и UI-представление.

Новая характеристика добавляется записью в реестр YAML/API без миграции `fact_assertions`, при этом для вычислимых характеристик по-прежнему потребуется поддерживаемый вычислитель (его нельзя создать одной строкой без подходящего инструмента). Если нет инструмента, применяется опрос отельера или статус `unknown`.

## 6. Источники и границы достоверности

| Источник | Использование | Сложность / ограничение |
|---|---|---|
| OSM + Overpass | здания, координаты, береговые объекты, пляжи, парки, инфраструктура | возможны пропуски и устаревшая разметка, публичные серверы ограничены |
| Valhalla (walking) | длина и время пешеходного маршрута | необходим роутинг-профиль и актуальный граф, учитывать ошибки трассы |
| Wikidata + Wikipedia | история здания, год и исторические описания | сопоставление с конкретным зданием обязательно, отсутствие записи не означает отсутствия истории |
| Wikimedia Commons GeoData | геопривязанные фотографии окружения | фото подтверждает вид с точки съёмки, **не вид из конкретного номера**; хранить атрибуцию и лицензию |
| Mapillary | уличные панорамы/снимки там, где есть покрытие | отдельный ключ и соблюдение условий API; необязателен для запуска |
| Муниципальные источники | стройки, перекрытия, фестивали по адресу и датам | для Сочи сначала нужно проверить наличие пригодного API/файлов, права и актуальность |
| Отельер | политика питомцев, шум, направления окон, номера и этажи | самоотчёт, сохраняется исходный ответ и история пересмотра |

Для stage-1 «строительство рядом» допустимо только как реально подтверждённое событие с геометрией и сроком. При отсутствии реестра — `unknown`, а не «строек нет». Фестивали и перекрытия не интерпретируются как гарантированный шум, а только как предупреждение об активности района.

Все коннекторы поддерживают кэш, указание User-Agent, rate limit, retry с экспоненциальным backoff и уважение `429/Retry-After`. Отсутствие сети не ломает чтение заранее собранного snapshot.

## 7. Логика агентов

Оркестратор получает `(hotel_id, requested_features, visit_window)` и строит план исполнения через feature registry. **Он не выбирает произвольные URL и не запускает произвольный код модели**; разрешены только зарегистрированные инструменты.

Подпроцессы:

1. `SourceDiscovery`: поиск потенциальных источников и проверка связи с конкретным отелем.
2. `GeoEngine`: работа с координатами, маршрутами и временными событиями; расчёты вне LLM.
3. `EvidenceExtractor`: извлечение структурированных утверждений с точными ссылками на исходный фрагмент.
4. `Verifier`: проверка типов, единиц, дат, совпадения объекта и конфликтов.
5. `HotelierDialogue`: выбор наиболее ценных уточняющих вопросов, ответы и структурирование нескольких полей.
6. `Resolver`: выбор итогового состояния по политикам, без стирания исходных утверждений.

Рекомендуемый путь: детерминированная обработка и шаблоны в demo mode; подключаемая LLM для свободных ответов и планирования в real mode. Любой LLM-вывод проходит строгую JSON-схему, проверки и является кандидатом, а не фактoм.

## 8. Геоаналитика: точные правила

- Внутренние координаты хранятся как WGS84 `(lat, lon)`; геометрия и расстояния в PostGIS (порядок координат при импорте GeoJSON — `[lon, lat]`).
- `coast_straight_m`: кратчайшее расстояние от отеля до береговой линии, с фиксацией версии OSM-геометрии; не равно доступу к пляжу.
- `beach_route_m` / `beach_walk_minutes`: ближайший **доступный пешеходный вход на пляж**, маршрут по пешеходной сети. Если нет маршрута — `unknown`, прямое расстояние показывается отдельно.
- `dog_park_walk_minutes`: маршрут до реально отмеченной площадки/парка для собак, а не до любого зелёного участка.
- `room_window_azimuth_deg`: сведения об ориентации конкретного типа номера; направление «на запад» — ещё не гарантия заката.
- `sunset_view`: только `reported` или `estimated`, если нет доказательства конкретного номера/этажа, времени года, линии обзора и препятствий. Сценарий «только с 5-го этажа» хранится на `room_type`/`floor`.
- `active_construction_nearby`: геометрическая близость к строительным работам **и** пересечение дат поездки с периодом работ; неизвестные интервалы отмечаются отдельно.
- `noise_risk`: индикатор вероятного риска с причинами (дорога, стройка, фестиваль), не объективное измерение тишины внутри номера.

Обязательные тесты: пересечение временных интервалов, координатный порядок, георасстояние, невозможный пешеходный маршрут, устаревшая карта, контекст этажа и номера.

## 9. Отельер: цикл уточнения

Триггеры: `unknown`, существенный `conflicted`, `stale`, низкое доверие при важном фильтре пользователя.

1. Система формирует вопрос с контекстом, без наведения на ответ, например: «Разрешены ли собаки? Если да, есть ли ограничение по весу и дополнительная плата?».
2. Отельер отвечает свободно: «С собаками до 12 кг можно; уборка 1500 ₽ за весь заезд; кошек не принимаем».
3. Извлекатель создаёт **несколько кандидатных значений**: `dogs_allowed=true`, `pet_max_weight_kg=12`, `pet_fee=1500 RUB/stay`, `cats_allowed=false`. Оригинал сохраняется.
4. Валидация проверяет единицы, контекст, отрицания, типы; при неоднозначности предлагает подтверждение.
5. После подтверждения система формирует `reported` или `verified` по политике; при конфликте старое доказательство не стирается.

Один текстовый ответ не обязан менять одну-единственную характеристику. Повторный ответ создаёт новую версию; доступны журнал и отмена некорректного решения.

## 10. Обработка конфликтов

Конфликт существует, если одновременно актуальны два несовместимых утверждения **для одного объекта, номера/этажа и периода**, например `pets_allowed=true` и `pets_allowed=false`. Значения для разных типов номеров, этажей и дат **не конфликтуют**, а являются контекстно разными.

Решение учитывает: авторитетность источника для конкретного поля, дату действия политики, точность привязки, независимость свидетельств, подтверждение отельером и ручную проверку. Не считать численное confidence единственным критерием. Решение содержит `reason`, `reviewer_id`, `decided_at`; все исходные записи сохраняются.

## 11. Поиск и объяснения

На первом этапе реализовать машинный контракт поиска (UI позже). Natural-language parser извлекает структуру:

- жёсткие ограничения: регион, вес питомца, сроки, время пешком;
- мягкие предпочтения: тишина, история здания, терраса;
- потребность в уточнении: конкретный номер, этаж, формулировка «у моря» без метрики.

Поиск использует только `resolved_fact` и не выдаёт `unknown` за соответствие. В выдаче по каждому критерию: `match | partial | mismatch | unknown | conflicted`, `explanation`, `fact_ids`, `source_ids`, `method`.

Требования не выполнимы одновременно → система показывает компромиссы, а не сочиняет подтверждённые варианты.

Существующая `POST /v1/agent/chat` в Go остаётся; адаптер направляет запросы нового типа в `POST /api/v2/intelligence/search`. Свайпы остаются работающими и не влияют на объективную истинность фактов.

## 12. Целевая техническая архитектура

```text
Telegram Mini App / future web UI
            |
         Go API (existing BFF, auth, swipes, profiles)
            |
         /api/v2/intelligence/*
            |
  Intelligence service (Python / FastAPI)
    |          |          |
  planner  evidence    search/resolver
    |          |          |
    +------ background worker ------+
                   |
          connector registry
          OSM, Wikidata, Commons,
          routing, hotelier, city sources
                   |
        PostgreSQL + PostGIS
       shared server / isolated schema
                   |
                 Redis
         queue + job control
```

**Обоснование:** сохраняем действующий Go API как точку доступа к продукту; Python — прагматичен для извлечения и геоинструментов; одна PostgreSQL-база, но изолированная схема `intelligence`, без дублирующего независимого SQLite-продукта. Конкретный язык модуля может быть изменён после аудита кода, но внешние контракты стабильны.

### Системные инварианты

- Системные справочники и доказательства — серверный источник истины.
- Snapshot-импорт идемпотентен; повторный job не плодит дубли.
- Данные пользователя и отельера не доступны через общедоступные endpoints.
- Операции enrichment асинхронны (202 + `job_id`), чтения не ждут внешних сайтов.
- Логи не содержат Bot Token, необработанных персональных данных или секретов.
- Предусмотрены `GET /health`, `GET /ready`, миграции и versioned API.

## 13. Критерии качества и приёмки

**Предлагаемые пилотные пороги**, не фактически измеренные результаты:

| Показатель | Цель к концу этапа 1 |
|---|---|
| Объекты в каталоге | 20 реальных отелей с дедупликацией и координатами |
| Работающие внешние источники | минимум 3 разных семейства; успешный тест и snapshot |
| Признаки в реестре | не менее 12, включая динамические и географические |
| Происхождение отображаемых значений | 100% имеют source, observed_at, method и статус |
| Конфликты | 100% заложенных в тестовом наборе конфликтов обнаружено |
| Geo | проверены расчёт прямого расстояния и пешеходного маршрута или явный unknown |
| Отельер | ответ с 3+ полями корректно разобран на демонстрационном кейсе |
| Тестовая разметка | минимум 60 вручную проверенных пар объект×признак, включая негативные и unknown |
| Фактические метрики | accuracy/precision, coverage, abstention, conflict recall и hotelier escalation вычисляются и публикуются; результат не подменяется целевым |
| Startup | `docker compose up --build`, seed без сетевой загрузки, доступное API |
| Security | отсутствует открытый production endpoint для изменения фактов |

Целевое время демонстрационного старта — до 3 минут после готовности Docker-образов, без обязательного обновления всех источников. Пределы скорости/качества должны быть измерены, а не объявлены достигнутыми заранее.

4. OpenAPI 3.1, JSON examples, CLI/HTTP сценарии для демо.
5. Feature registry с поддержкой новых полей, схема БД и журнал решений.
6. Unit/integration/e2e тесты с имитацией отказов и контрактными тестами Go↔Intelligence.
7. Результаты оценки с разделением реальных подтверждённых и синтетических тестовых данных.
8. `README` с режимами `demo` и `live`, известными ограничениями, инструкциями для разработчика и жюри.

## 15. Риски, требующие проверки до реализации

- **Стройка и события в Сочи:** доступность машинно-читаемых, датированных, геопривязанных муниципальных данных не подтверждена. Первое действие — аудит и decision log. Альтернативно использовать один верифицированный датированный CSV/GeoJSON для демонстрации и не выдавать его за live.
- **Историчность здания:** объект в Wikidata может быть соседним зданием; обязательная привязка по адресу/геометрии и ручная выборка.
- **Фотографии:** отсутствие фото, ограничение лицензии или недостоверная привязка не позволяют доказывать вид из номера.
- **Роутинг:** публичные сервисы могут быть недоступны; нужен региональный кеш или собственный ограниченный граф.
- **Свободные ответы отельера:** LLM может ошибаться в отрицаниях, условиях и валютах; сохранять оригинал, требовать подтверждения неоднозначного.
- **Существующий исходник:** полное техническое соответствие контрактов Go ещё необходимо проверить по фактическим файлам; решение опирается на публичный README и имеющийся демо-архив.

## 16. Декомпозиция этапа 1

| Подэтап | Результат | Критерий завершения |
|---|---|---|
| 1.1 Аудит | Карта действующих Go-эндпоинтов и источников | Реальные контракты/таблицы сопоставлены без домыслов |
| 1.2 Данные | PostGIS-схема, 20 отелей, registry, snapshots | Миграции + импорт идемпотентны |
| 1.3 Коннекторы + geo | 3 live коннектора, алгоритм маршрута | Доказательство доступно вплоть до URL и координат |
| 1.4 Агенты + отельер | Planner, verifier, questions, conflict resolver | Сценарии unknown/conflicted/reported работают |
| 1.5 Поиск + качество | API, evaluation, отчёт | End-to-end тест и README воспроизводятся с чистого старта |

**Definition of Done этапа:** отдельный разработчик без специальных доступов запускает сервис и демонстрационные данные, выполняет `search`, просматривает конкретный источник и метод факта, создаёт конфликт, отвечает от лица тестового отельера, повторяет поиск и видит изменение объяснения. Результат не требует LLM API key.

## 17. Нефункциональные требования и качество кода

- **Работоспособность:** чтение сохранённых фактов и демонстрационный поиск не зависят от доступности внешнего источника или LLM.
- **Производительность:** проектный ориентир p95 для поиска по подготовленному каталогу из 20 объектов — менее 500 мс на тестовом стенде; фактический результат измерить в отчёте. Enrichment выполняется асинхронно с отдельным timeout для каждого источника.
- **Наблюдаемость:** correlation/request ID сквозь Go→Intelligence→worker, structured logs, счётчики ошибок коннекторов, `GET /ready` и метрики jobs.
- **Конфигурация:** secrets только env / secret storage; `.env.example` с комментариями к переменным и без реальных токенов. Все публичные URL и гео-пороги задаются конфигурацией.
- **Чистота реализации:** небольшой набор модулей с чёткой ответственностью, типизированные интерфейсы, `gofmt`/`go test`, `ruff`/`pytest`, OpenAPI contract tests. Не создавать AI-«пояснительных» комментариев или мёртвых заглушек; документация описывает поведение, не имитирует его.
- **Адаптивность будущего клиента:** первичные контракты должны поддерживать мобильные экраны и читаемые reason codes, но верстка полного кабинета в данном этапе не обязательна.
- **Непрерывность:** смена API/схемы допускается только вместе с миграцией, обновлением OpenAPI и контрактными тестами совместимости существующего Go UI.
