# Пользовательские сценарии и сквозные проверки

**Принцип:** сценарии определяют поведение системы; UI полноценного клиента готовится после готовности API.

## US-T1 — подбор по свободному описанию

**Как путешественник**, я ввожу «тихий номер, море в 10 минутах пешком, можно с собакой 12 кг, красивый закат», чтобы получить не обещание AI, а доказанный подбор.

1. Parser выделяет `beach_walk_minutes <= 10`, `dogs_allowed=true`, `pet_max_weight_kg >= 12`, `quiet` как мягкий критерий, `sunset_view` как уточняемый критерий.
2. Из базы выбираются варианты, сопоставление проводится по `resolved_fact` с актуальностью на даты поездки.
3. Выдача показывает `match/partial/mismatch/unknown/conflicted` для каждого требования и доказательство; неизвестные значения не засчитываются как совпадения.
4. Если ни один вариант не выполняет все жёсткие ограничения — объяснить отсутствие точного совпадения и предложить компромиссы, не скрывая их.

**Acceptance:** результаты детерминированы по фиксированному snapshot; видно откуда взялись все заявленные совпадения.

## US-T2 — изучить историю здания

Турист открывает «История здания» → видит нормализованное описание + ссылку Wikidata/Wikipedia + степень привязки к фактическому зданию. При сомнении видит «История не подтверждена для этого адреса».

## US-T3 — доказательство вида на закат

Турист выбирает номер: для отеля указаны западные окна, но нет фото и подтверждения этажа. Система показывает `estimated`, а не `verified`. При ответе отельера «закат виден только в номерах 5-го этажа» создаётся утверждение с context `floor=5` и `reported`.

## US-H1 — ответ отельера сразу на несколько признаков

**Дано:** вопрос «Допускаете ли собак и кошек, какой вес и какая доплата?».

**Когда:** отельер отвечает: «Собаки до 12 кг допускаются, кошки нет. Доплата 1500 рублей за весь заезд».

**Тогда:** сохраняется исходный текст и создаются кандидаты по полям `dogs_allowed=true`, `cats_allowed=false`, `pet_max_weight_kg=12`, `pet_fee={amount:1500,currency:RUB,unit:stay}`. Неоднозначность помечается и требует подтверждения; другой отель не меняется.

## US-H2 — отельер исправляет старое условие

В старом каталоге `pets_allowed=false` (дата политики неизвестна). Отельер сообщает о новом разрешении. Система фиксирует обе версии и открывает конфликт либо, если точные интервалы не пересекаются, формирует новую временную версию. Старый raw evidence не удаляется.

## US-A1 — агент собирает данные

Admin запускает enrichment по одному hotel_id. Задача возвращает `202 + job_id`, worker вызывает разрешённые инструменты, сохраняет ответы источников и нормализованные кандидаты, verifier проверяет идентичность, построение и даты. Job переходит в `completed`, `partial` или `failed` с детальным отчётом по инструментам.

## US-A2 — агент анализирует стройку в даты поездки

У события строительства есть площадка и период. Турист приезжает на даты, не пересекающиеся с периодом работ: `active_construction_nearby=false` только **относительно конкретного перечня проверенных событий**, но без доступного полного реестра глобальное утверждение «строек нет» запрещено. Внутри периода система показывает предупреждение с расстоянием/ссылкой, а не гарантирует шум.

## US-A3 — недоступный источник

Overpass или Wikidata отвечает `429/timeout`: worker соблюдает retry policy; API чтения продолжает обслуживать seed/snapshot. Для новых значений появляется `unknown` либо `stale`; данные не заменяются догадками.

## US-A4 — новая характеристика

Admin добавляет YAML-описание `has_bicycle_storage` с типом boolean и политикой `hotelier`. API возвращает признак без миграции; вопрос отельеру и подтверждённое значение попадают в профиль. Если указан вычислитель, которого нет в реестре tools, конфигурация не активируется, а не выполняет произвольный код.

## US-A5 — оценка качества

Reviewer размечает набор hotel×feature. Система вычисляет coverage, precision/accuracy по размеченным парам, proportion unknown, conflict recall на контролируемых противоречиях, question escalation rate. Отчёт отделяет фактические метрики от целевых критериев.

## US-A6 — актуализация

Построенный рядом объект меняет препятствие обзора; после изменения входной геометрии перерасчёт `sunset_view` помечает предыдущее значение `stale`, создаёт derived-кандидат новой версии и не утверждает автоматически, что вид из номера изменился, пока это не подтверждено.

## US-S1 — безопасность прав

Отельер A пытается ответить на вопрос отеля B — `403`. Неавторизованный пользователь пытается разрешить конфликт — `401/403`. User ID из браузера без проверенной подписи Telegram не используется как доверенная идентичность.

## US-S2 — чистый запуск

После `docker compose up --build` demo seed содержит набор отелей и доказательств, чтобы поиск, конфликт, вопрос отельеру и метрики воспроизводились без API-ключей и сети. Отдельная команда запускает live enrichment с соблюдением ограничений источников.

## Демонстрационный маршрут жюри (7–10 минут)

1. Показать объект и URL/время полученного факта.
2. Рассчитать маршрут до пляжа и показать геометрию/метод.
3. Выполнить запрос на естественном языке, получить объяснимую выдачу.
4. Включить заготовленный конфликт источников.
5. Отельер отвечает одной фразой с несколькими условиями; система сохраняет варианты и утверждение.
6. Повторить поиск и показать, как меняется объяснение без потери исходных источников.
7. Показать метрики по размеченной выборке и режим запуска без ключа LLM.
